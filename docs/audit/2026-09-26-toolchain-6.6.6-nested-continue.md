# cyrius-doom — Audit: the cyrius 6.6.6 bump — nested-`continue` miscompile + AGNOS build break (2026-09-26, v0.35.6)

> **Found by the toolchain bump, not by a review round.** cyrius 6.6.6 refused to compile
> `sprite_render_all` (`too many continue statements in loop (max 8)`). Chasing *why* the limit had
> moved turned up a miscompile that shipped in every doom binary from at least v0.31.5 through
> v0.35.5, a residual shape that 6.6.6 still miscompiles, and an AGNOS build that had not compiled
> since v0.35.5. Everything below was measured, not inferred from changelogs.
>
> **Method**: (1) minimal self-contained probes (raw `write` syscalls, no stdlib, so the compiler is
> the only variable) compiled under both 6.6.2 and 6.6.6; (2) a static scanner over every source
> compiled into doom (`src/`, `vendor/`, `tests/`, `fuzz/`, `benches/`, and the resolved `lib/`) for
> the two defective shapes; (3) a 41-capture render A/B + 12 behaviour fingerprints, with a
> **control build** (the old compiler given continue-free, semantically-correct source) to attribute
> every changed pixel; (4) historical scans of the tree at earlier commits.
>
> Baseline: v0.35.5 rebuilt from `git archive HEAD` on its own pin (6.6.2) — **sha256-identical** to
> the local `build/doom` (`e4c2d09d…`), so it is a proven true-pin reference. The working tree was
> never used as a baseline.

---

## 1. `continue` bound to the wrong loop in a nest (cyrius ≤ 6.6.2; fixed 6.6.3)

**User-visible severity: HIGH** — a monster or item standing partly behind a nearer wall could be
drawn as **nothing at all**.

### Mechanism (cyrius 6.6.3 CHANGELOG, confirmed by probe)

`continue` jumps were recorded in **one flat 8-slot patch array shared by every nesting level**, and
every loop restarted the slot index on entry. A nested loop's continues therefore overwrote the slots
its enclosing loop had already recorded:

- the enclosing loop's first *k* continues were **never patched — they compiled to no-ops** and fell
  through into the code they were meant to skip;
- the nested loop's continues were re-patched to the **enclosing** loop's latch, abandoning the rest
  of the nested loop *and* the rest of the enclosing body.

Strictly lexical: it bites only when the enclosing loop records a `continue` **before** the nested
loop. A second half: a `while` nested in a `for` inherited for-mode and sent its `continue` to the
`for`'s step.

### Probe matrix — outer `continue` before the nest, innermost loop owns a `continue`

Correct result for every row: `noop=0 inner=8 mids=4 outers=2`.

| Shape | 6.6.2 | 6.6.6 |
|---|---|---|
| for > for > for | ✗ `1 3 0 0` | ✓ |
| for > for > while | ✗ `1 3 0 0` | ✓ |
| **for > while > for** | ✗ `1 3 0 0` | **✗ `1 3 0 0` — still broken, §2** |
| for > while > while | ✗ `0 2 0 0` | ✓ |
| while > for > while | ✗ `0 4 0 2` | ✓ |
| while > for > for / while > while > for / while > while > while | ✓ | ✓ |

Two-level controls pass on both compilers whenever either side of the steal is missing (no outer
continue before the nest, or no continue in the nested loop). `while` nested in `for` owning a
`continue`: 6.6.2 `hits=3 fors=0`, 6.6.6 `hits=9 fors=3` (correct).

### doom sites — complete inventory

Scanner over `src/`, `vendor/`, `tests/`, `fuzz/`, `benches/` **and** the resolved `lib/` (stdlib +
bsp): four sites, all in `src/`. `lib/` is clean.

| Function | Shape | Under 6.6.2 | Disposition (v0.35.6) |
|---|---|---|---|
| `sprite_render_all` | for (7 continues) > for (2) | `lump < 0` and `psz < 8` dead; a fully-occluded column (`clip_t > clip_b`) **dropped the rest of the sprite** | 6.6.6 binds it correctly; nest reduced 9 → 6 continues (the new cap, §3) |
| `render_clip_band_build` | for (3) > for (1) | `dx2 < x1` dead (harmless — the overlap range empties); a column where the drawseg is farther than the sprite **stopped that drawseg occluding at every later column** | 6.6.6 binds it correctly; unchanged |
| `render_blit_psprite` | for (4) > while > for (2) | `scr_x` guards dead (harmless — `framebuf_pixel` bounds-checks); an off-screen row abandoned the column | **still miscompiled on 6.6.6** → range clamps, §2 |
| `st_draw_patch_shaded` | for (4) > while > for (2) | same as the psprite decoder | **still miscompiled on 6.6.6** → range clamps, §2 |

**How long**: `sprite_render_all` and `render_clip_band_build` have had this shape since `c9228dd`
(2026-07-08, v0.31.5 — the per-drawseg band work). A scan of that commit also flags
`render_masked_one` (since restructured) and a 10-continue nest in `sprite_render_all`. The loop's
own comment attributing its "dead `scr_x` guards" to a 6.1.37 miscompile "fixed in 6.2.x" was this
same defect; it was never fixed before 6.6.3. The comment is corrected in place.

**It also explains v0.35.1's open "Known issue".** RC-G1 found that an inline thing scan (a nested
`for` with `continue`) inside `doors_tick` made a closing door stop descending — control "left the
iteration without entering the block" — while "the obvious small shape behaves correctly in
isolation", and shipped the scan as the `door_thing_blocks` helper without a diagnosis. `doors_tick`
records `if (sec < 0) { continue; }` **before** the nest; the inline scan's `continue` stole that slot
and jumped to `doors_tick`'s own latch. The isolated repro lacked an outer `continue` ahead of the
nest, which is the steal's precondition. The comment in `doors.cyr` now says so; the helper stays.

## 2. Residual — `for > while > for` still miscompiles on 6.6.6 (upstream-open)

When an outer `for` records a `continue` before a nested `while` that contains a `for` owning a
`continue`, 6.6.6 keeps the pre-6.6.3 behaviour exactly (row 3 of the matrix). Minimal reproducer:

```
var noop = 0; var inner = 0; var mids = 0; var outers = 0;
fn probe() {
    for (var a = 0; a < 3; a += 1) {
        if (a == 0) { continue; }
        if (a == 0) { noop += 1; }
        var m = 0;
        while (m < 2) {
            for (var b = 0; b < 3; b += 1) {
                if (b == 1) { continue; }
                inner += 1;
            }
            mids += 1;
            m += 1;
        }
        outers += 1;
    }
    return 0;
}
# expected noop=0 inner=8 mids=4 outers=2 ; 6.6.2 and 6.6.6 both give noop=1 inner=3 mids=0 outers=0
```

**Root cause, read from the compiler source** (`src/frontend/parse_ctrl.cyr`, identical at the
`6.6.6` tag and at 6.6.6-5; no later commit touches the file). The word at `0x18F898` is overloaded:
it is both the patch array's **next-free index** and the while/for **mode flag** (0 = while-mode).
6.6.3's second half makes `PARSE_WHILE` declare while-mode by saving the word and zeroing it
(`:210-211`). But `PARSE_FOR` derives its base from that same word, `cfwb = scfw; if (cfwb < 1)
cfwb = 1` (`:468`, `:484`). So a `for` nested under a `while` sees 0, takes base 1, and starts
writing at slot 0 — on top of the enclosing `for`'s recorded continues. That is the pre-6.6.3 steal,
reintroduced by the `while`. The fix needs the mode flag and the slot high-water mark to stop sharing
one word.

**doom's workaround** — both decoders now clamp their column and row ranges instead of testing each
pixel with `continue`, so no `continue` sits in the innermost `for` for the defect to steal (the
outer `for` keeps its lump-bounds continues, which the matrix shows compile correctly without an
inner one). This is also cheaper: **`status_render` 132.7 → 118.2 µs (−10.9%)**, same-compiler A/B.

**Proof of exactness**: `fuzz/fuzz_patchdraw.cyr` is a differential fuzzer. It draws each hostile or
edge-straddling patch through the real decoder and through a continue-free reference that keeps the
original per-pixel tests, then requires byte-identical framebuffers. 20,000 iterations × 5 seeds: 0
mismatches. The default-seed run alone draws 34.3 M reference pixels and clips 832 K columns and
82.3 M rows, and the harness fails itself as VACUOUS if either axis never clips. **Mutation-proven**: all 8 range-*shrinking* off-by-ones (every bound, both decoders) are
caught. The one range-*expanding* mutant survives because `framebuf_pixel` independently rejects the
extra off-screen column — output-equivalent, not a blind spot.

## 3. New limit — at most 8 `continue`s per loop NEST (6.6.3+)

The patch array is now partitioned across the nest instead of reused, so the cap moved from 8 per
loop to 8 per nest. `sprite_render_all` had 9. Reduced to 6 by merging the paired guards into the
file's own `a || b` idiom and deleting `psz == 0`, which is unreachable once `psz < 8` is live.
Nothing else in the tree exceeds the cap (scanner, all compiled sources).

## 4. The AGNOS build had not compiled since v0.35.5

**Severity: HIGH (release process)** — AGNOS is the primary deployment target.

`vendor/setu.cyr` still bound `tcp_socket()` / `sock_accept()` results with the pre-6.6.0 boxed
`Result` form (`var s = f(); result_unwrap(s)`). The 6.6.x value form refuses that. The file is
compiled **only under `--agnos`**, so:

- v0.35.5's bump (6.5.4 → 6.6.2) migrated `src/` and never saw it. **Reproduced**: v0.35.5 on its own
  pin fails `cyrius build --agnos` with the same six errors.
- CI and the release workflow build Linux only. Every job was green.
- The local `build/doom_agnos` was the Aug-1 v0.35.4 binary. v0.35.5 was never rebuilt or
  QEMU-run for AGNOS, and its banner still said `v0.35.4`.

**Fix**: the three binds migrated to `var t, v = f(); result_unwrap(t, v)` (grep shows those were
the only `Result` binds in the file; its three `is_ok(f())` uses are already correct, since a single
argument receives the tag). Plus a CI **`Build (AGNOS target)`** compile gate, which the release
workflow inherits through `needs: [ci]`.

**QEMU**: `doom-directmap-smoke.sh` boots v0.35.6, the WAD loads and the frame renders. Its
floor-band gate reports FAIL, which is a harness bug (§6). A 6×-block diff of the screendump
against the Linux `--ppm` frame is **64,000 / 64,000 exact**.

## 5. Checked and clean

- **`CYRIUS_DCE=1` PT_LOAD defect (fixed 6.6.3)**: it bites only when DCE moves the end of code
  across a 2 MB bucket. v0.35.5's release build places RW at `0x600000` with and without DCE, and
  E1M1 / E1M5 / E1M9 / title render identically. **The shipped v0.35.5 binary was not affected.**
  On 6.6.6, DCE removes code instead of NOP-sledding it: release `build/doom` is **375,440 B**
  (131,936 B eliminated).
- **Lock**: 6.6.6 writes `cyrius.lock` sorted (readdir-order fix, 6.6.3) and records the toolchain;
  39 entries (+`alloc_cx.cyr`), 39 verified / 0 failed from a clean `rm -rf lib`.
- **vani 1.1.2 → 1.2.5**: hardening only on the `audio_*` functions doom calls (null-handle guards,
  idempotent `audio_close`, `avail_min == 0` rejected; doom passes 1024). Every return is still a
  plain `i64`, so 1.2.3's value-form break (`vani_result_unwrap`) cannot reach doom. The AGNOS
  `sys_snd_config` branch moved intact into `audio_set_params_fmt`.
- **bsp 1.2.1 → 1.2.5**: doom's bsp surface (`point_on_side`, `is_subsector`, `subsector_idx`,
  `node_child_l/r`) is byte-identical apart from comments. `asr` is now a thin alias for native `>>>`,
  bit-identical per bsp's differential. `regression_asr.tcyr` pins literal floor values, so it keeps
  an independent reference. 1.2.4's `fx_div` fix cannot reach doom, which calls no `fx_*` function.
- **Stdlib**: only what 6.6.6 bundles. The local sakshi (2.5.5), patra (1.15.0) and yukti (2.3.12)
  repos are ahead of the bundle (2.5.2 / 1.14.3 / 2.3.11) and were deliberately not taken.

## 6. For upstream (not changed here)

1. **cyrius** — file §2's reproducer and root cause: `for > while > for` continue binding, still
   open at 6.6.6 (the `0x18F898` index/mode-flag overload in `parse_ctrl.cyr`).
2. **agnos `scripts/smoke/doom-smoke.sh`** — the direct-map floor-band gate samples
   `(ex*scale, ey*scale)` from the origin. blit#39 **centres** the frame, and on the current
   2048×2048 framebuffer that puts the 6× frame at `(64, 424)`, so the gate reads console text and

   no offset). Fix: offset by `((w - 320*s)//2, (h - 200*s)//2)`.

   the `for > while > for` residual, and the 8-per-nest cap.
